# Architecture

Fanout Code is a macOS desktop app for one developer who runs several AI coding agents at once across several projects.
A window shows one project or one workspace (several linked projects). Each project has a Kanban board; each card is a
task that owns a real terminal session and a markdown memory folder and moves through Spec → Plan → Build → Review →
Test → Commit → Done, handing back to the developer at the end of every stage.

This document is the map. The rules are in `CLAUDE.md` and `.claude/rules/`; the decisions in `docs/adr/`; the design
in `docs/superpowers/specs/2026-10-24-team-code-design.md`. Each implementation plan fills in its sections.

## The three layers

**Core** (`crates/fanoutcode-core`, lib `fanoutcode_core`) has no Tauri dependency. Plan 01 gives it `error` (one `Error`
enum serialised as its message), `ids` (validated id newtypes with fixed prefixes), `domain` (every shared type, serde
and specta derived), `db` (SQLite, migrations, app-scope settings rows), `recent` (the start screen's recent list) and
`windows` (the registry of which window shows which container). **Shell** (`src-tauri`, package `fanoutcode`, lib
`fanoutcode_lib`) owns `AppState` (the database connection and the window registry behind `std` mutexes), builds
windows from Rust, exports commands and events through tauri-specta, and wraps the OS keychain. **Webview** (`src/`)
renders; it reads state from module stores (`createStore`) with `useSyncExternalStore` and talks to the shell only
through the generated `src/lib/bindings.ts`.

Plan 03 adds the pipeline to the core. `pipeline::transition(task, action, ctx)` and `pipeline::move_to` are pure:
they return `Effect`s, with every stage's entry effects defined once in `pipeline/enter.rs`. `pipeline::apply`
persists the stage, state, archive flag and timeline in one SQLite transaction, mirrors them to the task's `index.md`,
and hands the external effects (sessions, worktrees, tests, helpers) back to the shell, whose `effects::dispatch`
forwards them to Plans 04 and 05. `pipeline::detect_handback` reads a `Stop` for the stage's sentinel line and
`handback::chip_text` is the source of the hand-back chip texts (`src/test/fixtures/handback.json` mirrors them).
`memory` owns task folders (atomic writes, unreadable files set aside as `.bad`, a missing folder never recreated);
`prompts` layers the shipped stage templates under app and project overrides; `roster` holds the shipped subagents;
`settings` resolves the key table task → project → workspace → app → default; `views::layout` edits pane trees. The
shell's task commands lock the database, compute, apply, release the lock, dispatch, then emit `task-changed` and
`needs-you`.

Plan 05 adds observation. In the core: `hooks` (the per-task hook commands, `HookSpec`, the event-log parser, plan
steps and `Step N · role:` dispatches, subagent attribution, the chip feed, the subscriber registry), `git` (the `git`
binary only: status, numstat, show, base, Done check, watch filter), `worktree` (both conventions and
`settings_for`), `changes` (the task's change set: hook edits, Bash-call windows, manual includes, persisted in
`task_files`), `testrun` (the owned test runner with a shared replay buffer), `helpers` (metered single-turn calls
through livespec-core: naming, briefs, spec watcher, commit drafts, the LiveSpec lane plan and run), `cost`
(transcript usage once per message, hourly buckets per task, stage, model and agent, scoped summaries) and `activity`
(the board card snapshot). In the shell: `hooks_tailer` tails `<app_data>/events/<task-id>.jsonl` from saved cursors
(replayed at launch, before any window) and hands each event to `hook_feed`, which sets the chip state through the
pipeline, feeds the change set, the cost ledger and the activity tracker, emits `team-event` and publishes to
`hooks_tailer::subscribe` subscribers (Plan 04 registers there); `git_watcher` watches each task's repos with a
500 ms debounce, rebuilds the change set, emits `git-changes`, moves a Commit-stage task to Done once its files are
committed and triggers the spec watcher in Review; `observation` records the base on Build entry and runs
`CreateWorktree`; `helpers` runs `RunHelper(kind)` one slot per task and kind; `provider` resolves livespec-core
providers from `model_provider` plus LiveSpec's own `<app_config>/livespec.json`.

## Persistence

SQLite at `<app_data>/fanoutcode.db` (WAL, foreign keys on), migrated at startup by `db::open` from
`crates/fanoutcode-core/migrations/00NN_<name>.sql`, where NN is the owning plan; applied versions are recorded in
`schema_migrations`, one transaction per file. Settings are rows of the `settings` table keyed by scope (ADR 0002);
Plan 01 writes the app-scope keys `theme`, `worktree_convention`, `first_run_complete`, `open_windows` and `recent`;
the registered keys, their levels and defaults are `settings::keys` (Plan 03). `tasks` rows keep the full `Task` in
`json` beside the columns queries filter on; `task_timeline` is the source the `index.md` timeline mirrors.
The webview mirrors the theme and accent in `localStorage` only so the first paint is right before IPC returns.

## Security model

No secret crosses IPC: secrets live in the OS keychain under service `app.fanoutcode.desktop` (`src-tauri/src/secrets.rs`)
and `Secret` cannot be serialised. Every id that becomes a path matches `^[a-z]+-[0-9a-f-]{1,40}$`. CSP is
`default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; style-src 'self' 'unsafe-inline'; img-src 'self' data:`;
fonts are bundled, never fetched. Windows are created in Rust only; the webview capability cannot create windows.
Model and agent output renders only through `MiniMarkdown` or xterm.

## Errors

`fanoutcode_core::Error` has six variants: `Precondition` (an instruction shown verbatim), `Provider` (model, CLI or
network), `Io`, `Git`, `Db` and `Invalid` (bad id or malformed input). It serialises as its message, so a command's
error reaches TypeScript as `{ status: "error", error: string }`.

## UI primitives

`src/components/ui/` is the only place raw `<input>`, `<select>`, `<textarea>`, `<button>` and `<dialog>` appear
(ESLint enforces it). It holds the twenty-seven primitive families of spec §15.3 (plus `ComboboxList`, the list half of `Combobox`) as thin, token-styled wrappers over Radix (via
the unified `radix-ui` package), cmdk, Vaul, Sonner and dotLottie; every feature composes them and never styles a raw
control. Import from the barrel `@/components/ui`, which also exports `UiProvider` (tooltip provider and toaster,
mounted once at each window's root), `cx`, `focusRing` and the shared unions in `tokens.ts`. `PRIMITIVES` in the
barrel lists each family and the names it exports; `src/dev/primitives/registry.test.tsx` fails until every family has
an example page.

- Colour by prop (`tone`, `stage`, `swatch`, `status`) goes through the literal class maps in `tokens.ts`, never
  through template strings, so Tailwind sees every class. Colours themselves live only in `src/styles.css`.
- Animation reads `useReducedMotion()` from `src/lib/motion.ts`: springs become 150 ms eases and loops stop.
- A primitive has no business logic: it never imports `src/lib/bindings.ts`, a store or a feature, and it takes plain
  unions (`AgentStatus`, `StageToken`), not the generated `AgentState` or `Stage`.
- Dev only: `npm run dev`, then `#/dev/primitives` shows one page per primitive with a light/dark toggle. The gallery
  is not in the production bundle.
- Tests: `src/test/setup.ts` (jsdom gaps, jest-dom, cleanup) and `src/test/ui.ts` (`mockMatchMedia`, `setupUser`,
  `renderUi`).

## The board

`src/features/board/` is the Kanban board. The shell mounts `Board(BoardProps)` as tab zero and passes the window's
container, its projects, the resolved settings, the focused project and `onOpenTask(taskId, OpenTarget)`; the board
knows nothing about windows or views. Other features import only `src/features/board/index.ts`.

- **State.** `boardStore` (`store.ts`) holds view state: filters, settings, focus, swimlane order, the last drop.
  Tasks live in the shared `tasksStore` cache and are read and written through `taskCache.ts` alone. Columns,
  swimlanes and the mode are memoised selectors (`selectors.ts`) read with `useBoard`.
- **IPC.** `ipc.ts` is the only board file that imports `src/lib/bindings.ts`; tests mock that one module.
- **Moves.** A drag calls `moveTask` (`actions.ts`): the card moves at once, `tasks_move` decides, and a refusal puts
  the card back with an error toast. Order inside a column is derived (needs you, working, idle; flagged; priority;
  newest), never dragged.
- **Events.** `task-changed` from another container is ignored; `team-event` and `git-changes` feed the card's last
  line, current file and team (`activity.ts`); the elapsed time is one shared ticker whose snapshot is a string, so
  a card re-renders only when its text changes.
- **Workspaces.** `workspace_board` and `workspace_project_layer` choose swimlanes, one project at a time or mixed.
  Swimlane order and collapsed rows are remembered per container in localStorage.
- **Motion.** Cards animate between columns with Motion `layoutId`, the destination column glows for `GLOW_MS`, and
  the Done column plays a one-shot dotLottie. `.lottie` files are never inlined (`vite.config.ts`), because the CSP
  blocks fetching a data: URL.

## Sessions and terminals

Every task's agent and every plain terminal is a PTY the app owns (Plan 04, spec §7.1–7.3).

- **Core** (`fanoutcode_core::sessions`). The core holds everything testable without a terminal:
  - the scrollback ring (`ScrollbackBuffer`, 10,000 lines by default);
  - the 60 Hz `Batcher` and the `FlowControl` high/low water marks (1 MiB / 256 KiB unacknowledged);
  - the `Pty` / `PtySpawner` seam with `fake` doubles;
  - `SessionDriver` with `OwnedDriver`, the only driver this release (ADR 0004);
  - the graceful `stop::run` (exit keys, 5 s, kill);
  - the generated per-task settings file under `<app_data>/claude-settings/` (hooks, status line, deny rules; the
    app never writes a project's `.claude/`);
  - the `claude`, `codex` and shell launch builders;
  - `IdleTracker` and `InjectQueue` (prompts wait until the agent is idle);
  - `SessionRegistry`, which allows one attached pane per session;
  - `TerminalTheme` (the value of the `terminal_theme` setting).

  Session rows are in `db::sessions`.

- **Shell.** `pty.rs` implements `PtySpawner` with portable-pty. Each session gets three threads: a reader that stops
  at a gate while flow control pauses it, a flusher that parks while idle, and a waiter that reports the exit once.
  Output reaches the webview as raw bytes on a `Channel<TerminalBytes>`. `session_service` launches primary
  sessions and terminals, takes `StartSession` / `EndSession` / `InjectPrompt` from `effects::dispatch`, and hears
  every hook event through `hooks_tailer::subscribe` (`note_hook_event`: a `Stop` makes Claude Code idle and sends
  the next queued prompt). It also runs the Codex quiet-time ticker, stops sessions, and warns at quit. Closing a
  window detaches its panes; the processes keep running. At launch every stored session is marked exited, and the
  next open resumes the task's Claude session with `--resume`. A primary session that exits on its own (not
  through a stop) moves its card to Idle or needs you (`sessions::state_after_exit`).
- **Webview** (`src/features/views/`).
  - `terminalStore` tracks each session's attach state as this window sees it: attaching, attached, elsewhere, or
    exited. It also tracks the pending prompt count and coalesces acks.
  - `TerminalPane` owns one xterm through `useXterm`. xterm is lazy-loaded and uses WebGL, falling back to canvas.
  - The colours come from the `--term-*` variables of the palette `terminalTheme.ts` picks, so hex values stay in
    `styles.css`.
  - A session held by another pane shows `TerminalPlaceholder` (Bring here / Bring back).

## The task page and dock

A task opens in a pane as `TaskPage` (`src/features/task-page`), which Plan 06's `PaneContentHost` renders for
`PaneContent::Task` and whose `TaskPageHandle` receives the task chords (⌘⏎, ⌘E, ⌘⇧A, ⌘J, ⌘⇧J, ⌃`).

- **Task records** stay in Plan 06's `tasksStore`; the page reads and writes them only through
  `task-page/taskSource.ts`. Page-local state (settings, queued action, cost, context meter) is `taskPageStore`.
- **Sessions**: the page calls `sessions_open` (idempotent: start or resume) for Plan through Commit and keys
  `TerminalPane` on `primary_session`, so Start fresh session remounts the terminal.
- **Decisions** are pure functions with tests: `primaryActionFor`/`forwardActionFor` (the button per stage and
  hand-back, shared with the palette and card menu), `dock/tabRules.ts` (visible tabs, default tab, stage entry),
  `dock/placement.ts` (⌘⇧J per Team placement), `dock/memory.ts` (which memory file, when to re-read).
- **Spec stage**: `spec-editor` binds LiveSpec's draft and notes panes (copied into `src/livespec/`) to `spec.md`
  with a 500 ms autosave; `SpecSession` debounces `livespec_analyze`, saving first; Approve flushes the save and
  refuses to advance when it failed.
- **Dock** (`src/features/dock`): Memory, Team (Plan 09's `renderTeam` slot), Changes, Ticket, Test, Commit, bottom
  or right, tab and height remembered per stage (`localStorage` `fanoutcode.dock`). `DockSplit` animates grows with
  `transitionFor`.
- **Changes** (`src/features/changes`): `git_changes`/`git_diff` into a CodeMirror 6 merge view (unified or side by
  side), the working side saved with `git_file_write`; review.md notes are line decorations whose cards are React
  portals into block widgets. A `git-changes` event over unsaved edits marks the file stale (Reload or Overwrite).
- **Test** attaches to the run through `tests_run` (start-or-attach with replay). Entering Test (a board drag,
  Approve changes) and Run tests start the run in the shell (`Effect::RunTest`, the same start-or-attach), and
  `test-started` makes an open tab attach to a run it did not start. **Commit** reads `git_drafts`, offers Commit
  only with "Fanout Code may commit" on, and Draft again (`tasks_draft_commits`) after a failed draft. **Ticket** reads
  the generated `jira_*` commands.
- Every IPC-touching store takes its command set as a parameter; `src/lib/ipcResult.ts`'s `live(...)` builds one over
  the generated `commands` that resolves to the value and rejects with the error string.

## The Team canvas

The Team tab (`src/features/canvas`, spec §10.7) draws a task's team from `plan.md` and its hook event log. Plan 08's
dock and Swap body render it through `renderTeam`; Plan 06's `PaneContentHost` renders `CanvasPane` for
`PaneContent::TeamCanvas`.

- **Model, pure and DOM-free**: `events.ts` (accessors over `HookEvent`, tool-call pairing, de-duplicated seqs) →
  `attribution.ts` (agents from `SubagentStart` and `Step N · role:` dispatches) → `files.ts` (edits, deltas, shared
  files) → `steps.ts` (status from plan.md ticks, owners, tool line, progress, cost) → `model.ts` `deriveCanvas` →
  `graph.ts` (hub graph or flow canvas, and the `layoutKey` that decides when to re-lay out). `adapters.ts` is the
  only reader of Plan 05's `PlanDoc`, `RepoChanges` and `CostSummary` field names. Replay derives from a prefix of
  the log (`replay.ts`).
- **Store**: `canvasState.ts` holds one reference-counted entry per open task and re-derives on every input change;
  `store.ts` loads it (`hooks_list`, `hooks_plan_steps`, `git_changes`, `cost_summary`, `settings_get`,
  `canvas_positions_get`) and keeps it live (`team-event`, `task-changed`, `git-changes`, `cost-updated`);
  `layoutRunner.ts` debounces elkjs layouts (150 ms) and saves positions (500 ms) through `canvas_positions_set`.
- **Layout**: `layout.ts` runs elkjs (loaded on first use) — stress plus an overlap pass for the hub graph, layered
  left-to-right for the flow canvas with agents docked below; `positions.ts` applies Auto re-flow or Pinned.
- **Rendering**: React Flow (`components/TeamCanvas.tsx`) over plain card components (`components/cards/`), edges
  between facing handles, a 300 ms spring (150 ms ease under reduced motion), Outline mode, the drill-in panel (By
  file and Event stream lenses) and the replay scrubber. `#/dev/canvas` is a dev-only playground fed from fixtures.
- **Smoke suite**: `npm run e2e` runs Playwright (WebKit, installed into `node_modules`) against the Vite dev server
  in `e2e` mode, where `src/main.tsx` installs `e2e/fixtures/mockTauri.ts` before the first render. A command the
  app calls at load without a handler there fails the suite by name.

## Workspaces and integrations

- **Record and file.** `fanoutcode_core::workspace::store::WorkspaceStore` owns the record in SQLite; the
  `<name>.fanoutcode-workspace.json` file is a mirror, written through while it lives in app data and marked dirty
  (saved on ⌘S with the sidebar focused, or when its window closes) elsewhere; reopening a dirty record keeps the
  record. A watcher reports edits made on disk (`workspace-file-changed`).
- **Opening a file from elsewhere** goes through `workspace::import`: `preview_open` reads it once (nothing is
  written), lists roots, policy, agents, instructions, settings and references with problems; `confirm_open(token,
approved_doc_ids)` imports exactly that buffer. Only the record's own unchanged file reopens without review
  (`open_file`). Roots that are `/`, the home folder or its ancestors, or Fanout Code's data are refused; file and folder
  references are approved one by one; Jira links are never imported.
- **Linking.** At a task's first session start `workspace::launch::bind_if_first_start` fixes its linked roots (the
  stage action that starts it binds first, `pipeline::prepare_action`, so its prompt already lists them) and
  records `(project id, canonical root)` pairs (`task_links`). Protection is decided by project id
  (`policy::protected_roots`, fail closed) and becomes `Edit(//<root>/**)` deny rules plus the Bash guard
  (`fanoutcode guard <roots-file>`, `workspace::guard`), both written into the generated Claude settings at every launch.
- **Prompts** take the workspace's policy, protection, briefs, references (only trusted, readable ones) and stage
  instructions through `workspace::launch::fill_prompt_ctx`.
- **Context docs** are fetched on demand into `<app_data>/context/<project|workspace>-<id>/`; every network hop goes
  through `workspace::url_guard` (no local or link-local addresses, private ranges only for trusted docs, each hop
  pinned).
- **Jira and Confluence** (`fanoutcode_core::jira`): the site is the `jira` setting (written only by `jira_link*`); the
  token is in the keychain under an account derived from the linking scope and is sent only to the origin it was
  verified against.

## Cross-task file awareness

Plan 11 (spec `docs/superpowers/specs/2026-10-25-cross-task-file-awareness-design.md`) keeps tasks that work in one
checkout from writing over each other's uncommitted changes, and lets tasks in separate worktrees plan around each
other. Every rule is in the core; the shell gathers inputs and applies what the core returns.

- **Core** (`fanoutcode_core::overlap`). `mod.rs` holds the shared types (`Relation`, `PendingDecision`, `Decision`,
  `OverlapRow`).
  - `claims` builds the claims file of a shared repo (every dirty, attributed path of an active task) and its path;
    `grants` the per-task grants file (`File` or `AllFiles` against one other task, pruned once its claims go);
    `notes` the per-task note inbox.
  - `check` is the `fanoutcode claim-check` hook: allow, or deny with the reason for Claude and a `ClaimDenied` line
    in the task's own event log; it fails open and drains the inbox into `additionalContext` on an allowed call.
    `git_rules` is its second rule set for shell commands that would stage, commit, restore, stash, reset or clean
    claimed paths.
  - `compute::overlaps_for` derives a task's `task_overlaps` rows from the claims files, the other tasks' footprints
    and change sets, and the stored rows (decided relations, open decisions and notes survive a recompute).
  - `store` is the `task_overlaps` CRUD, including `taken_over_paths` for Done detection
    (`changes::done_by_takeover`); `footprint` the `task_footprint` rows (a plan's `## Files` and the change set).
  - `denial` turns a `ClaimDenied` line into open decisions and nothing else; `decide` is the developer's answer as a
    pure outcome (grant, relation, the mirror relation on the other task, timeline lines, prompts, `OverlapDecided`).
    A Replace marks the path `TakenOver` on the replacer and `TakenOverBy` on the task that lost it; only the
    replacer's row drops the path from the other task's Done check.
  - `others` writes "Others working here" for the stage prompts and the soft notes between worktree tasks;
    `integrate` reads the session's `Stop` after the integrate prompt and excerpts each task's intent; `prompts` holds
    every overlap prompt text.
- **Hook files under app data.** `<app_data>/claims/<repo-key>.json` (one per shared repo, rewritten atomically on
  attribution or `git status` changes and at launch), `<app_data>/grants/<task-id>.json` and
  `<app_data>/notes/<task-id>.json`. `workspace::launch::launch_extras` adds the hook to the generated Claude
  settings as a `PreToolUse` hook on the file tools (and on Bash with the git guard on) running
  `fanoutcode claim-check <task-id> <grants> <notes> <log> <0|1> <claims…>` (`src-tauri/src/main.rs`). The two
  "Working together" project settings switch the ask and the git guard off; then the hook only logs.
- **Shell.** `overlap_sync/` rebuilds the claims files and each task's overlaps (`mod.rs`), records a `ClaimDenied`
  stop and pins the task to needs-you while a decision is open (`pin.rs`), applies `overlap_decide` (`decide.rs`:
  grants, relations, the takeover move between change sets, timeline and log lines, the go-ahead and the other
  task's note) and attributes Codex and shell edits as `Observed` (`hookless.rs`). `overlap_integrate.rs` runs
  "Bring <base> in", reads the footprint from `plan.md`, fills "Others working here" and queues the soft notes.
  `commands/overlap.rs` exports `overlap_list`, `overlap_decide` and `overlap_pending_input`;
  `commands/overlap_integrate.rs` the integration commands from the Done card. `overlap-changed` keeps the webview
  current.
- **Webview** (`src/features/overlap/`). `overlapStore` holds each task's rows and counts from `overlap_list` and
  `overlap-changed`. The Overlap dock tab (`DockTab` `"overlap"`, shown only while a task has an overlap, amber and
  opened once while a decision is pending) lists the files grouped _Needs you_ and _Also touched by others_ beside
  the decision pane (both diffs, the four answers, Continue) and, during a merge hand-back, the integrate pane. Board
  cards, view tabs, the Changes rows and the sidebar carry the counts and relation chips.
