# Team Code 10: Workspaces and Integrations Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Build the workspace record and its JSON mirror, the linking machinery (bound roots, `--add-dir`, protected-root deny rules, the Bash guard hook, prompt fragments), the Jira and Confluence clients, context docs, and the workspace settings and Costs UI.

**Architecture:** Everything stateful lives in `teamcode_core::workspace` and `teamcode_core::jira` over the contract's SQLite tables; the database is the source of truth and `<name>.teamcode-workspace.json` is a mirror (write-through while in app data, explicit save elsewhere). The shell adds thin `workspaces_*`, `context_docs_*` and `jira_*` commands, keychain glue, and a `guard` CLI mode of the app binary that the `PreToolUse` hook calls. The webview gets `src/features/workspace/` with module stores plus the settings and Costs panels; Plan 06's sidebar sections and Plan 08's Ticket tab render the same stores.

**Tech Stack:** Rust (rusqlite, serde, reqwest with rustls, notify, url, tokio; wiremock and tempfile in tests), Tauri 2 commands exported by tauri-specta, React 19 + TypeScript strict, module stores on `createStore` read with `useSyncExternalStore`, Vitest.

**Spec:** `docs/superpowers/specs/2026-10-24-team-code-design.md` (§4.1–4.3, §12, with §6.8, §7.3, §10.6, §13, §14 where they touch workspaces). **Contracts:** `docs/superpowers/plans/2026-10-24-team-code-00-overview-and-contracts.md`. Names from the contracts document are used verbatim; names this plan introduces are collected under "Proposed contract additions" at the end.

## Global Constraints

- Three layers: `crates/teamcode-core` never depends on Tauri; `src-tauri` stays thin; the webview has no state library and uses module stores read with `useSyncExternalStore` (§3, §14).
- IPC types are generated by `tauri-specta` into `src/lib/bindings.ts`; hand-written mirrors are forbidden (§15.1).
- Raw `<input>`, `<select>`, `<textarea>`, `<button>`, `<dialog>` appear only under `src/components/ui/`; hex colours and inline colour styles appear only in the theme file. ESLint fails the build otherwise (§15.3).
- Semantic Tailwind tokens only: `bg-page`, `bg-bar`, `bg-well`, `bg-card`, `border-line`, `text-ink`, `text-mute`, `text-accent`, `text-ok`, `text-warn`, `text-bad`, plus `stage-spec|plan|build|review|test|commit|done` (§11.1).
- Secrets live in the OS keychain under service `app.teamcode.desktop`, never cross IPC (§14). (The one exception is the token the developer types into the link form, which travels webview → shell once and is never returned.)
- Every id that becomes a path matches `^[a-z]+-[0-9a-f-]{1,40}$` before use (§14).
- Model and agent output renders only through `MiniMarkdown` or xterm, never `innerHTML` (§14).
- The app never commits, merges, rebases, pushes or deletes branches on its own (§6.6).
- Nothing a user triggers takes longer than 250 ms to respond; `prefers-reduced-motion` turns springs into 150 ms eases and stops loops (§11.3). Network calls (Jira, Confluence, URL fetch) run off the UI thread and show a pending state.
- File size budgets: component under about 200 lines, store under 300, Rust module under 500 (§15.1).
- Naming: components `PascalCase.tsx`, lib and stores `camelCase.ts`, Rust `snake_case`; IPC commands `domain_verb` in snake_case; events `kebab-case` (§15.1).
- Commits follow Conventional Commits (§15.4). Every task ends with the quality gates in §15.4 passing for the code it touched: `npm run typecheck`, `npm run lint`, `npx vitest run`, `cargo test --workspace`, `cargo clippy --workspace --all-targets -- -D warnings`.
- The generated Claude settings file contains only the hooks (including the read-only guard), the status line, the protected-root permission rules and, when needed, the background-isolation key; `--add-dir` is granted only for projects the developer put in the workspace (§14). Hooks and prompts the app installs never leak into the developer's normal Claude Code usage (§2).

## Review Focus

1. **A workspace file edited on disk while the record has unsaved changes.** Reload must not silently discard the developer's edits: `reload` refuses while `dirty` unless the caller passes `discard_unsaved`. Test `reload_refuses_when_dirty_unless_discard` (Task 3).
2. **A write hidden inside a nested shell**, e.g. `sh -c 'rm -rf /w/api/dist'` or `bash -lc "cd /w/api && npm i"`. The guard must unwrap `sh|bash|zsh -c <string>` and evaluate the inner command. Test `nested_sh_c_is_unwrapped` (Task 7).
3. **The task's home project is removed from the workspace** while the task is bound to it. `link_status` must not panic or report `Bound`; it reports `Changed` with every root removed. Test `status_when_home_project_left_workspace` (Task 5).
4. **A Jira site URL typed with a trailing slash or a `/browse/KEY` suffix** (pasted from the browser). The client normalises to the origin so request paths do not double up. Test `new_normalises_trailing_slash_and_browse_path` (Task 12).
5. **Relocating a missing project onto a folder that is already another project's root.** Relocation must not create two `Project` records for one folder. Test `relocate_project_rejects_root_of_another_project` (Task 3).

## Calls made in this plan (spec ambiguities resolved)

- **Deny rules are `Edit(//<root>/**)` only.** The spec names `Edit`, `Write`, `MultiEdit`, `NotebookEdit`; Claude Code's current permission docs state that `Edit(path)` rules govern every built-in file-editing tool and that `Write(path)`, `MultiEdit(path)` and `NotebookEdit(path)` rules never match. One `Edit` rule per protected root blocks all four tools; the UI label still reads "file tools blocked". Absolute paths use the documented double-slash form.
- **`Workspace.policy` is the single source of truth for the linking policy.** Plan 03's settings registry has no `link_policy` key (contracts A12); callers read `Workspace.policy` through `workspaces_*`. Protected targets are `WorkspaceProject.protected`.
- **Binding is recorded by `Task.links_bound_at`** (Plan 01's domain field, column in Plan 03's `0003_core`; contracts A11): `None` until the first session start, then set together with `workspace_id` and `linked_roots`. Codex and shell tasks bind with an empty root set so they "see only their home project".
- **Policy changes apply to sessions started from now on.** The deny list and guard are baked into the per-task settings file at launch; the settings UI says so. "Links changed, start a fresh session to apply" is shown for membership changes only.
- **Confluence pages and URL docs are fetched on demand into `<app_data>/context/<doc-id>.md`**; prompts list the cached file's path under the references heading, and the context folder is added to `--add-dir` so the agent reads it when it needs it. Nothing long is pasted into the PTY.
- **Confluence uses the Atlassian site credentials linked for Jira** (same site, same API token); no separate Confluence link.
- **The Jira default site is the `jira` setting at workspace scope**, so projects without their own inherit it through `settings::resolve`. Site URL and email are settings; the token's keychain account name is carried in the setting value, the token itself is in the keychain.
- **Conversion moves views** (re-parents the project container's views to the new workspace) so pane ids and session attachments survive; the old container is left with no views, which "never migrated back" permits.
- **Workspace-level agent definitions live in the workspace file** under `agents`, alongside `prompt_fragments`, so a shared file carries the roster additions Plan 03's `roster::resolve` unions in.
- **Out of this plan's scope but driven by its data:** §4.3's LiveSpec retrieval order (home project first, linked projects second, home snippets weighted higher) belongs to Plan 05's LiveSpec levels and reads `Task.linked_roots`; grouping of linked-repo changes by repo belongs to Plan 05's change set and Plan 08's Changes tab.

### Task 7: Guard rule matching for write-shaped Bash commands

**Files:**
- Create: `crates/teamcode-core/src/workspace/guard.rs`
- Test: `crates/teamcode-core/src/workspace/guard.rs` (`mod tests`)

**Interfaces:**
- Consumes: nothing beyond `std`.
- Produces:
  - `pub struct GuardInput { pub command: String, pub cwd: PathBuf }`
  - `pub enum GuardRule { Redirect, Program(&'static str), SedInPlace, PerlInPlace, Git(&'static str), PackageInstall(&'static str), FindDelete }`
  - `pub enum GuardDecision { Allow, Deny { root: PathBuf, rule: GuardRule, reason: String } }`
  - `pub fn evaluate(input: &GuardInput, protected: &[PathBuf], home_dir: &Path) -> GuardDecision`
  - `pub fn deny_reason(root: &Path, rule: &GuardRule) -> String` → `"Team Code: <root> is read-only in this workspace; this shell command looks like it writes there (<rule>). Read it freely; to change it, ask the developer to change the linking policy."`

Matching rules (the algorithm the signature does not determine):

```
1. Normalise each protected root: strip trailing '/'; also accept the '~/…' spelling when the root is under home_dir.
2. Tokenise the command respecting single quotes, double quotes and backslashes; split into segments on
   unquoted ';', '&&', '||', '|', '&', newline. Treat '(' … ')' and '$(' … ')' as part of the enclosing segment.
3. If a segment's program is sh|bash|zsh|dash with a -c (or -lc/-ic…) argument, evaluate the argument string
   recursively with the same cwd; a Deny inside is the segment's decision.
4. Walk segments with a running cwd (start = input.cwd). 'cd <p>' / 'pushd <p>' updates it (absolute replaces,
   relative joins, '-' or no argument leaves it). Strip leading VAR=val words and the wrappers
   sudo, env, command, nohup, time, nice, xargs before reading the program name.
5. A segment "references" a root when its text contains the root followed by end, '/', whitespace or a quote,
   or when the running cwd is inside the root.
6. Write-shaped:
   a. Redirect: an unquoted '>', '>>', '>|', '&>', '&>>' or 'N>' (N digit) not followed by '&'; its target
      is the next word, resolved against the running cwd. Deny when the target is under a protected root.
   b. Program in {rm, rmdir, mv, cp, ln, mkdir, touch, tee, truncate, dd, shred, unlink, chmod, chown, chgrp,
      install, rsync, patch}. For cp, mv, rsync, install, ln only the last positional (destination) decides;
      for the rest any positional under a root, or the cwd being inside a root, decides.
   c. sed with an argument starting with '-i' or '--in-place', or a short cluster containing 'i'; perl likewise.
   d. git whose subcommand (skipping -C <path>, -c k=v, --git-dir=…) is in {add, commit, checkout, switch,
      restore, reset, rebase, merge, cherry-pick, revert, stash, clean, rm, mv, am, apply, pull, push, init,
      clone, worktree, submodule, notes, replace, update-ref, symbolic-ref, filter-branch, gc, prune}, or is
      branch/tag with a positional argument or one of -d -D -m -M -f. fetch, status, log, diff, show, blame,
      grep, ls-files, rev-parse, describe and branch/tag listings are read-only.
   e. Package installs: npm {install, i, ci, add, uninstall, un, remove, rm, update, up, link, unlink, dedupe,
      prune}; pnpm {add, install, i, remove, rm, update, up, link, unlink, dedupe, prune}; yarn {add, install,
      remove, upgrade, link, unlink}; bun {add, install, i, remove, rm, update, link}; pip/pip3 {install,
      uninstall}; uv {add, remove, sync, pip}; poetry {add, remove, install, update, lock}; cargo {add, remove,
      update}; go {get, mod}; composer {require, remove, install, update}; bundle {add, install, update}.
      Deny when the segment references a root (including via --dir/--cwd/-C/--prefix arguments) or the cwd is inside one.
   f. find with -delete or -exec/-execdir whose path arguments reference a root.
7. First Deny wins; otherwise Allow.
```
